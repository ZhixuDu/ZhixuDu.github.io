vLLM Throughput and Latency Overhead of an MoE Mamba Model

What is the throughput and latency overhead of a mixture-of-experts Mamba model in vLLM?

Answer

The overhead is small but present. In Swimba (Du et al., 2026), decoding with vLLM under identical settings shows Swimba-14B with slightly lower throughput and higher latency than Nemotron-H-8B across the tested batch sizes and input-output lengths, with as low as a 10% slowdown.

The benchmark sweeps batch sizes of 1, 16, 32 and 64 and input-output sequence lengths of 256, 512, 1024 and 2048 on a single 40GB A100 GPU, using vLLM with the Transformers backend engine. Throughput is measured as tokens processed or generated per second, and latency as time from request to the start of generation. Figure 4 plots throughput against batch size for each sequence length with an inset of the Swimba/Nemotron throughput ratio; Figure 5 plots latency against sequence length for each batch size with the corresponding ratio. The paper describes latency trends as similar across sequence lengths.

Swimba-14B adds 4 experts with top-1 routing to every Mamba-2 layer of the 52-layer Nemotron-H-8B hybrid. Its FLOPs per token differ from the baseline by under 0.2%, so the measured slowdown is larger than FLOPs predict. The authors attribute the gap to routing overhead. They also cite prior benchmarking indicating that adding more experts while keeping the number of active experts fixed leaves throughput and latency largely unchanged, which they take to suggest favorable scaling to more experts; this was not measured for Swimba itself.

In exchange, Swimba-14B's average accuracy across nine benchmarks is 70.81 versus 69.47.

Setup

vLLM with the Transformers backend on a single 40GB A100; batch sizes 1, 16, 32, 64; input-output lengths 256, 512, 1024, 2048; Swimba-14B (4 experts, top-1) versus Nemotron-H-8B under identical settings.

Serving cost was measured on one GPU with the vLLM Transformers backend, without custom MoE kernels, for a single 4-expert top-1 configuration.

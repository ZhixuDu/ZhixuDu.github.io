Oracle Draft Length and Headroom in Speculative Decoding

How much speedup is left if speculative decoding knew the ideal draft length per block?

Answer

Du et al. (2026) estimate roughly 20% projected latency headroom on MATH-500 relative to a fixed 16-token draft window. Their map drafting sets each draft block to the upcoming run of positions where Qwen2.5-0.5B matches a Qwen2.5-72B reference, capped at 16 tokens. Projected latency was 3.99 seconds per response, against 4.98 for the fixed window and 4.69 for confidence-adaptive drafting, a reduction of up to 19.9%, with accuracy of 69.40% versus 69.00% for both baselines. The map is supplied as an oracle, so this measures available headroom rather than a deployable method.

The saving comes from avoided rejections. Map drafting proposed 301,691 draft tokens across the dataset versus 447,731 for the fixed window, 32.6% fewer, while accepted draft tokens were similar (268,577 versus 269,286) and mean target calls were similar too (57.62 versus 56.87 per response). Fixed-window drafting spends much of its draft work on tokens the target then discards. The adaptive baseline stops a block when a proposed token's probability falls below 0.4.

Across 36 timing scenarios that rescale the per-position cost, the small-model speed and the verification overhead, map drafting stayed faster than fixed-window and adaptive drafting by 8.3-24.7% and 7.3-18.4%. The logical FLOP ledger moves the other way: map drafting used 112.07 TFLOPs, fixed drafting 154.30 and adaptive 140.52, all above 72B alone at 101.92, because rejected drafts and verification add arithmetic even as they shorten sequential time.

Map fallback occurred on 169 speculative responses. The paper reads small accuracy differences as outcomes of this backend, not as evidence that draft length changes an exactly preserved target policy.

Setup

All 500 MATH-500 problems with Qwen2.5-0.5B-Instruct as the small model and Qwen2.5-72B-Instruct as the target, greedy decoding, a common 1,024-token output cap, and symbolic-equivalence checking (Math-Verify). The map is supplied as an oracle from a fresh greedy 72B response; its acquisition is excluded from resource counts. Baselines: TokenCascade-style confidence routing at four thresholds, fixed 16-token drafting and confidence-adaptive drafting. Runs use a PyTorch 2.9.1 backend in bfloat16 with the target on four A100 80GB GPUs; latency is projected from official Qwen2.5 vLLM A100 benchmarks; 2,000 bootstrap resamples of problems.

Oracle draft lengths from a 72B greedy reference on all 500 MATH-500 problems, with projected rather than measured latencies.
